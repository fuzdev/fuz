# Signing

Ed25519 signing for release verification. Manifest format and the verification
flow: ./release_format.md. Cutting a release: ./release_workflow.md. Signing the
release log head: ./release_log.md. Why and against what: ./security-model.md.

## Architecture

Signing is split so the `fuz` consumer links **verification only** — the
private-key side is never in its graph (`cargo xtask check-release`).

- **`fuz_crypto`** — verification and canonical JSON, pure crypto with no file
  I/O: `verify_signature`, `is_trusted_key` (constant-time), `Signature`, the
  signed-bytes types (§ Signed Bytes), `canonical_json`, and `PUBLIC_KEYS` /
  `WITNESS_KEYS`, generated by `build.rs` from `src/public_keys.json`. It links
  ed25519-dalek without `rand_core`, so it cannot generate keys.
- **`fuz_sign`** — the signing side: `generate_keypair`, the key file format
  (`parse_key_file` / `serialize_key_file`) and its loader (`load_signing_key`),
  `sign_manifest`, `sign_head`, and the `publish_*` flows. **No sign-any-bytes
  entry point**: every signature is over a typed document's signed bytes. Used
  by `fuzf tool publish` and `cargo xtask`.
- Key loading is `fuz_sign::key_file`; `cargo xtask key generate` writes keys in
  `crates/xtask/src/key.rs`, both through `fuz_sys::secure_file`.

**Protected against**: unsigned or wrongly signed binaries; a signature for one
kind of document passed off as another; key theft via file access (`0600`,
symlink refusal, atomic writes); TOCTOU on key loading (`O_NOFOLLOW`, fd-based
mode checks); canonical-JSON manipulation. **Not protected**: a compromised
build machine, a compromised backup (keys are unencrypted), side channels.

**Key protection**: file-only (never env vars — visible in
`/proc/*/environ`); `0600` checked on the open fd; seed and `SigningKey`
zeroized. The key lives only on the publisher machine — never on the forge or
any byte-serving host, which stores signed bytes and can't forge a signature.

## Key File Format

`$FUZ_HOME/config/signing.key` (default `~/.fuz/config/signing.key`, mode
`0600`):

```
fuz-signing-key-v1
public: <base64-encoded-32-byte-public-key>
seed: <base64-encoded-32-byte-seed>
created: 2025-01-15T10:30:00Z
```

Strict: exactly four lines, nothing trailing; raw 32-byte values in base64; the
derived public key must match the stored one. `v1` is unencrypted, the only
format (`v2`, encrypted, is deferred).

Every reader of the key — `cargo xtask key info` / `export`, `cargo xtask
publish`, `cargo xtask release-log`, `fuzf tool publish` — loads it through
`load_signing_key`: the `--key-file` path as given (without resolving the fuz
home), or the default above. It must be a regular file no other user can access,
opened without following a symlink; a failure is one error carrying the cause,
with a hint where there is something to do.

## Signature Format

```json
{
  "format": 2,
  "public_key": "base64...",
  "algorithm": "ed25519",
  "signed_at": "2025-01-15T10:30:00Z",
  "sig": "base64..."
}
```

- `format` is `SIGNATURE_FORMAT_VERSION` (2), matched exactly; anything else is
  `VerifyError::UnsupportedFormat`. Unknown fields are refused.
- Self-contained: the public key is embedded (no key-ID lookup); trust is the
  embedded `PUBLIC_KEYS` alone — verify never touches key files.
- `signed_at` is informational and **not signed**. Rollback protection is the
  semver no-downgrade rule, not timestamps.

## Signed Bytes

One release key signs more than one kind of document, so the signed bytes are
the kind's **domain tag** followed immediately by the document's canonical JSON
(no separator, length prefix, or trailing newline), signed with pure Ed25519
(RFC 8032 §5.1):

| Kind | Document | Tag |
| --- | --- | --- |
| `Manifest` | release manifest (self and per-tool) | `b"fuz-manifest-v1\0"` (16 bytes) |
| `ReleaseLogHead` | release log `head.json` | `b"fuz-release-log-head-v1\0"` (24 bytes) |

Canonical JSON escapes every control character, so the first NUL ends the tag;
neither tag prefixes the other or a JSON document, so a signature for one kind
can't verify as the other even over identical JSON. Test vector: seed 32 zero
bytes (public key `O2onvM62pC1io6jQKm8Nc2UyFXcd4kOmOsBIoYtZ2ik=`), message
`fuz-manifest-v1\0{"body":"known answer"}` →
`ROOhAsIQ0zWY7obTgqwNkLMTLGRipg8K12PgU/tPk04wd4mEEQUvX2PoEpu+jRaLxjoGdioBNqhalT1RyaQKCw==`.

The kind is never a loose argument: `SignedPayloadKind` is bound to the document
type by the `SignedPayload` trait, `SignedMessage::new(&payload)` is the one
constructor, and both signer and verifier take a `SignedMessage`. Changing a tag
or the envelope format invalidates every signature it covers. Co-signatures are
SSH signatures with their own namespace (§ SSH signatures).

## Canonical JSON

The deterministic serialization of signed documents (`fuz_crypto::canonical`):
keys sorted by UTF-8 bytes, no whitespace, ASCII-only strings, integer-only
numbers. serde_json isn't pinned; `serde_json_escaping_is_stable` guards the
escaping — if it fails after an upgrade, pin serde_json or change the format
(which invalidates existing signatures).

## Public Key Embedding

`crates/fuz_crypto/src/public_keys.json`, parsed at compile time:

```json
{
  "format": 1,
  "keys": ["base64-public-key"],
  "witnesses": [
    { "origin": "https://cosigner.example.com/log", "ssh_public_key": "ssh-ed25519 AAAA… comment" }
  ]
}
```

`keys` generates `PUBLIC_KEYS` (a build warning past ten keys). The optional
`witnesses` list generates `WITNESS_KEYS` — release log co-signer keys, each
paired with the origin it serves. **The checked-in file has no `witnesses`**, so
`fuz` requests no co-signature.

### Witness keys

Rules (`fuz_crypto::witness::check_witnesses`, compiled by both the crate and
`build.rs`):

- `ssh_public_key` is a `.pub` line: `ssh-ed25519`, the base64 key, an optional
  comment; the decoded blob must be `ssh-ed25519` with exactly a 32-byte key.
- `origin` is an `https://` URL in printable ASCII with a host and no comma,
  userinfo, query, fragment, or trailing slash. `fuz` matches it exactly (apart
  from trailing slashes), so the build refuses a form that could never match.
- An origin appears once; a key may serve several origins; an unknown field is
  a build error, in an entry or at the top level (where `_comment` and `_see`
  are allowed).
- **A witness key is never a release key**: the build refuses a key in both
  lists, and `is_trusted_key` reads `PUBLIC_KEYS` alone, so anything signed by
  a witness key is refused as untrusted.

## SSH signatures (`sshsig`)

A co-signature is made with `ssh-keygen -Y sign`, so a co-signer runs no code
from this project. `fuz_crypto::sshsig::verify_sshsig` verifies one armored
signature over one message, under one namespace, by one expected ed25519 key —
a strict subset of what `ssh-keygen -Y verify` accepts (the accepted grammar is
the module's rustdoc). The key inside must equal the expected key, and the
namespace must equal `fuz_release_log` for a co-signature.

Who co-signs and what their origin must serve: ./release_log.md § Co-signing.

## CLI Commands

```bash
cargo xtask key generate [--output <path>] [--force]   # default $FUZ_HOME/config/signing.key
cargo xtask key info [--key-file <path>] [--json]      # public key, created date
cargo xtask key export [--key-file <path>]             # the public key, for public_keys.json
cargo xtask key list-trusted                           # the embedded PUBLIC_KEYS
```

Releases are signed by the publish flow; there is no `key sign` / `key verify`.
Exit codes: `0` success, `1` any error (with a `hint:` where one applies), `2`
an unparseable command line.

## Key Rotation

Planned rotation, so installed binaries never lose an upgrade path:

1. `cargo xtask key generate --output ~/.fuz/config/signing-new.key`, then
   `cargo xtask key info --key-file …` for the public key.
2. Add it to `public_keys.json`, keeping the old key.
3. Build and release with the **old** key — the new binary trusts both.
4. Let users upgrade; then switch to the new key for future releases.
5. After a grace period, remove the old key from `public_keys.json`.

In the release log, the first head the new key signs appends it to the head's
`keys` list. The format has a `retired_at` field no command sets yet, and the
list never feeds a trust decision — step 5 is what retires a key.

**A compromised or lost key** can't follow this path: installed binaries trust
only their embedded keys, so every install must re-bootstrap
(./security-model.md § Key Compromise Response). Back the key up offline
(`cp`, then `chmod 600` on restore and `cargo xtask key info` to check).

## Testing

`fuz_crypto`'s own tests use a deterministic keypair (`test_keypair()`, seed
`[0u8; 32]`) trusted only under `#[cfg(test)]` inside that crate, and mint
signatures with a module-local raw-ed25519 helper (`sign_for_test`) — `fuz_sign`
depends on `fuz_crypto`, so the reverse edge would be circular.

**End-to-end trust in downstream tests** uses **dev-dependency-only**
features:

- `fuz_crypto/test_trust_anchor` — a runtime registry of extra trusted keys
  (`add_trusted_key_for_testing`), consulted by `is_trusted_key` only under the
  feature.
- `fuz_home/test_home_override` — an in-process `FUZ_HOME` redirect
  (`set_fuz_home_override_for_testing`), since `unsafe_code = "forbid"` rules
  out `set_var`.
- `fuz_artifact/test_binary_stubs` — `platform::test_stubs`, minimal
  executables for a target, since a publish and an install both hold each
  binary's header to the release's target.

`fuz_sign/tests/signed_trust.rs` enables them and drives publish →
`fetch_latest` / `fetch_version` / `install_tool` through the real signature
check, version floor, extraction, and install. Feature-off, the guarded code
doesn't exist, resolver 2 doesn't unify a dev-dependency feature into normal
builds, and `cargo xtask check-release` refuses any of them on a normal or
build edge. **Only ever enable them from `[dev-dependencies]`.**

To exercise publish + install with a throwaway key by hand:
./release_workflow.md § Local Testing.
